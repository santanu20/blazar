# 1. SYSTEM Overview

Detected project type: **hybrid** (HTTP gateway — `crates/pallama-gateway/src/lib.rs` `router()` on axum — plus CLI binary — `crates/pallama-cli/src/main.rs` `Cmd` enum on clap).

> Canonical documentation for **Pallama v0.6.1**. Statements below were verified against source unless tagged **INFERRED**. This file is the canonical source of truth for the product overview.

## Problem statement

Running large language models locally today fragments the user across incompatible runtimes:

| Pain | Concrete symptom |
|---|---|
| Engine lock-in | ollama ships a single forked llama.cpp; users of mistral.rs or SGLang must run and learn each engine's own server CLI separately |
| API lock-in | Each runtime exposes one API dialect; clients written for OpenAI, ollama, or Anthropic cannot freely mix |
| Opaque resource behavior | Context silently clamped (ollama's default 2048 ctx), VRAM/KV budgets not visible, models evicted without explanation |
| Modelfule/blob duplication | ollama copies GGUF weights into opaque blob layers, doubling disk usage and breaking other tools |
| Telemetry/cloud coupling | Runtimes that phone home or require accounts |
| Fork drift | Vendored engine forks lag upstream fixes and quant formats |

Pallama solves this: it is a **local-only, multi-engine inference server** that orchestrates official (unforked) `llama.cpp` (`llama-server`), `mistral.rs`, and `SGLang` behind a single gateway speaking **OpenAI, ollama, and Anthropic** wire APIs simultaneously. Local-only is a hard product property: no telemetry, no cloud endpoints, no accounts (login/logout commands are refused by design).

## Target users and roles

| Role | Interaction |
|---|---|
| Local developer | Uses `pallama` CLI or any OpenAI/ollama/Anthropic client pointed at the local HTTP gateway |
| Agent/tooling operator | Uses `pallama launch` to exec agent CLIs with base-URL environment pre-wired; uses tool-calling, JSON schema outputs, sessions |
| API-key administrator | When one or more `[[keys]]` exist in `config.toml`, manages named keys, scopes, quotas (rpm/tpm/daily_tokens/max_concurrent/weight) via `/api/keys` |
| Operator/SRE | Observes via `/api/ps`, `/api/why`, `/metrics`, `pallama doctor`, audit log, OTLP traces |

There is no multi-tenant cloud role: the gateway binds `127.0.0.1` by default and auth is optional (active iff any key exists).

## Core user workflows (happy paths)

1. **Install & first run**
   `pallama engine update` (sha256-verified official engine download, regression-gated; auto-rollback on >10% decode regression unless `--no-gate`) → `pallama pull qwen3-0.6b` (ollama registry shortname) or `pallama pull ggml-org/Qwen3-8B-GGUF:Q4_K_M` (HuggingFace `owner/repo:QUANT`) → `pallama serve` (daemon) → `pallama run <model>` (auto-pulls if missing).
2. **Point existing clients at it**
   OpenAI clients → `http://127.0.0.1:11435/v1/...`; ollama clients → `OLLAMA_HOST=http://127.0.0.1:11435 ollama list` works unchanged (re-point from 11434; a drop-in on 11434 is opt-in via `port = 11434` once ollama is removed); Anthropic clients → `/v1/messages`.
3. **Chat/generate with a model** — request hits gateway, is queued (priority/SLO), routed to a spawned per-model engine child process (`llama-server`, `mistral.rs serve`, or `python -m sglang.launch_server`), translated to the child dialect, and translated back to the requested wire API. Streaming and non-streaming both supported.
4. **Vision / embeddings / rerank / audio** — mmproj-carrying models serve images (projector lazily attached); `/v1/embeddings`, `/api/embed` (late chunking opt-in), `/v1/rerank`; Whisper transcription lane (`pallama whisper`).
5. **Fit-before-download** — `pallama fit <target>` previews VRAM fit and quant alternatives before pulling.
6. **Observability** — `pallama ps` (slots/ctx/ports/in-flight, load countdown), `pallama why` (trace investigation), `/metrics` Prometheus exposition, `pallama doctor` (grouped SYSTEM/GPU/ENGINES/MODELS/CHANNELS/RUNTIME checks).

## High-level architecture explanation

```
            ┌────────────────────────────────────────────┐
  clients ──▶│  pallama-gateway (axum, 127.0.0.1:11435)   │
 (OpenAI /  │  layers: request_log → auth → CORS →       │
  ollama /  │           body-limit(50MiB) → session-pin  │
  Anthropic)│  priority queue (EDF + WFQ) → translation  │
            └───────┬────────────────────────────────────┘
                    │ spawn/monitor/evict per model
            ┌───────▼────────────────────────────────────┐
            │  pallama-runtime supervisor                │
            │  per-model child processes:                │
            │   • llama-server (llama.cpp)      [gguf]   │
            │   • mistral.rs serve              [gguf/f16]│
            │   • sglang.launch_server          [safetensors]│
            └───────┬────────────────────────────────────┘
                    │ metadata, catalogs, profiles
            ┌───────▼────────────────────────────────────┐
            │  pallama-core: config.toml, SQLite store   │
            │  (engines/models/profiles/loras/usage/bench)│
            │  GGUF metadata parser, hardware probe,     │
            │  VRAM/KV math, profile (argv) compiler     │
            └────────────────────────────────────────────┘
```

- **One gateway, many engines.** The gateway terminates all client APIs; children speak only their native dialect. The `pallama-cli` binary drives everything (serve, pull, run, engine management).
- **Engine routing is data-driven** (`engine_kind.rs`): quantized safetensors (AWQ/GPTQ/FP8) route to SGLang only; GGUF routes to llama.cpp then mistral.rs; plain safetensors route by policy (Quality/Throughput → SGLang first, Latency → mistral.rs first). `engine_routing.mode = "manual"` pins a single active engine; model-level `engine` override wins over both.
- **State is explicit and local**: SQLite at `<data_dir>/pallama.db`, config at `~/.config/pallama/config.toml`, model files as plain `.gguf`/safetensors under `~/.local/share/pallama/models/` (usable by any external tool), engine binaries under `engines/`, per-child runtime secrets under `run/`.
- **Observability built in**: trace IDs (`plm-<hex>-<seq>`), access logs, Prometheus `/metrics`, OTLP export (opt-in), sentinel quality observations, `why` trace investigation.

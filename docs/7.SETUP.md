## Local development setup

1. **Toolchain:** Rust (stable). On a fresh source checkout, a zero-arg `cargo build` works; `scripts/bootstrap.sh --minimal` provisions a C compiler + Rust toolchain first (announced before acting).
2. **Clone and build:**
   ```sh
   git clone <repo> && cd blazar
   cargo build --release
   # binary: target/release/blazar
   ```
3. **Paths the daemon uses** (created on demand by `dirs.ensure()`):
   - `~/.config/blazar/config.toml` — configuration
   - `<XDG data>/blazar/` — `blazar.db`, `models/`, `engines/`, `run/` (per-child pid + child auth secret files, `daemon.log` — the daemon's own durable log, rotated to `daemon.log.1` at 10 MiB — and per-child `.sock` under `child_transport = "unix"`), `speccache/`, `sessions/`
   - Engine rows in `blazar.db` record their server binary **relative to the data dir** (`engines/<tag>/...`), so a data dir move/copy stays relocatable; the out-of-tree `local` lane (`BLAZAR_ENGINE_PATH`) keeps its absolute path.
   - XDG variables absent → falls back to CWD **with a loud stderr warning** (never silent).
4. **First engine + model:** `blazar engine update` then `blazar pull qwen3-0.6b`.

## Platform & hardware coverage (honesty rows)

What runs where — stated up front so "why doesn't lane X work here" is a
docs lookup, not a bug report:

- **Windows is first-class for the app and the llama.cpp lane** (winget,
  Scoop, `scripts/install.ps1`; Vulkan and CPU compute; CUDA when the
  driver census finds it). `blazar doctor` names what your machine actually
  serves each lane with.
- **The SGLang lane needs Linux or WSL2.** The upstream runtime depends on
  `uvloop`, which does not install on Windows — the lane's install and
  doctor output say so instead of failing mid-pip. Other lanes are
  unaffected.
- **NPU-class accelerators are not a lane yet.** Vulkan already covers
  Intel Arc / integrated GPUs for compute today; NPU (OpenVINO-class)
  support is an upstream-engine question tracked in
  `docs/research/2026-10-02-competitor-pain-points-audit.md`.

## Build process

- `cargo build --release` — workspace build (4 crates, resolver 2, edition 2021).
- `unsafe_code = deny`, clippy pedantic in CI (**INFERRED**: enforced via repo lint config).
- Engine binaries are NOT built by the workspace by default — `blazar engine update` downloads official artifacts (sha256-verified, regression-gated); `blazar engine build cuda|cpu` builds them locally (auto GPU-arch detection via `nvidia-smi`, host-compiler matching for nvcc, installs `bNNNN-cuda`-style tags with `llama-server`/`-quantize`/`-imatrix`/`-perplexity`/`-bench` binaries).

## Deployment flow

1. **End-user install (recommended):** curl|sh one-liner from the published repo (override via `BLAZAR_REPO`); Windows via winget (rustup provisioning included) or `scripts/install.ps1`; also Homebrew and Scoop packages (`packaging/`).
2. **Service:** `scripts/install.sh` can install a systemd unit; unit sets `RestartPreventExitStatus=3` so bind-conflict exits (code 3) never restart-loop.
3. **Run:** `blazar serve` (alias `start`) — binds `127.0.0.1:11435` by default (blazar's own port, never ollama's 11434; set `port = 11434` for an ex-ollama drop-in); port 0 = ephemeral.
4. **Upgrade:** `blazar upgrade [--version X] [--dry-run]` — sha256-verified self-upgrade.
5. **Rollback engines:** `blazar engine rollback` / `blazar engine use <tag>` — side-by-side tags, never destructive.

### GPU driver preflight (installer)

Before the engine lands, the installer censuses PCI GPU hardware (`lspci`, provisioned when missing) and — when the driver userspace is absent — installs it from **first-party distro repos only** (announce-then-act): NVIDIA via apt's `nvidia-driver` / pacman's `nvidia nvidia-utils`; dnf auto-installs `akmod-nvidia` only when RPMFusion is already enabled; zypper and all third-party-only lanes print the exact command instead of running it. AMD/Intel without a Vulkan ICD get the mesa Vulkan drivers. Every install ends with the loud chain: **REBOOT, then `blazar engine update`** — which auto-picks the newest CUDA build the installed driver supports (runtimes are bundled; no CUDA toolkit is ever installed). Opt out with `BLAZAR_AUTO_DRIVER=0`. Windows is advise-only: the PowerShell installer detects NVIDIA hardware without `nvidia-smi` and links the driver download. `blazar doctor` warns (`nvidia driver` / `vulkan driver` rows) whenever PCI GPU hardware is present but its driver is not.

### Multi-GPU sharding & admission

Automatic tensor parallelism: when weights plus KV exceed the best single card but fit the discrete cards per-rank, the SGLang lane plans the spawn across them (`--tp-size N`) and the fit ladder judges per-rank demand against the bottleneck card. The same planner awareness extends admission: a load that only makes sense sharded is judged against the combined GPU pool instead of the largest single card, and refusals say so (`even sharded across N cards (X GiB per rank)`). Manual pins (`tp_size`, `dp_size`, `pp_size`, `ep_size`, tensor split, device lists) always win — auto-sharding only fires when parallelism is unpinned. The llama.cpp lane has its own auto tensor-split for the same case, and the mistral.rs lane spans by layer mapping: it admits a load that exceeds the best single card yet fits the cards combined and lets the engine distribute layers itself (`--device-layers` omitted), which permits uneven splits a per-rank planner would refuse.

On all-NVIDIA boxes every sharded spawn is pinned: the child receives `CUDA_DEVICE_ORDER=PCI_BUS_ID` plus `CUDA_VISIBLE_DEVICES` naming the first N cards in PCI bus order, so ranks and cards stay aligned on mixed-memory pairs. Any doubt — non-NVIDIA or mixed-vendor census, probe short of ranks — leaves the child env untouched and the engine's own device mapping in charge.

Admission and queueing: when a model is saturated, Blazar parks requests behind bounded admission rather than allowing uncontrolled concurrency to inflate latency and destabilize the workload. Loads that no amount of waiting can fix — the admission floor exceeds every GPU budget even with the box empty — are refused immediately with the numbers and the levers (`blazar fit`, smaller ctx/slots, a larger card) instead of timing out in a queue.

### Best-of-N fan-out (per request)

`best_of` (2–4) is a request knob, not a config knob: send it as a body field on `/api/chat`, `/api/generate`, or `/v1/responses` bodies, or as the `X-Blazar-Best-Of` header on `/v1/messages` too. The gateway fans the request out to N parallel child candidates, judges them (schema-valid > `finish_reason: stop` > first), and returns the winner with usage summed across all candidates; the `X-Blazar-Best-Of` response header itemizes `asked/used/usage`. Streaming requests cannot be judged and are rejected with a teaching 400, as is the knob on `/v1/chat/completions` (byte-faithful passthrough lane — the buffered OpenAI lane is `/v1/responses`). The fan-out degrades to a single send under queue depth, no free decode slots, or bodies over 1 MiB (counters in `/metrics`: `blazar_bestof_fanouts_total`, `blazar_bestof_degraded_total`).

### Agentic cascade routing (per request)

`cascade` is a request knob on `/api/chat`: send `cascade: ["small-model", "big-model"]` in the body or `X-Blazar-Cascade: small-model, big-model` as a header (header wins and pins the order). Candidates are tried in order and each answer is judged against the same ladder best-of-N uses (2xx + requested schema + clean finish); the first pass is served and later candidates are never sent — a request the small model answers costs exactly one small-model call. When the body names the chain and at least two candidates have measured decode rates (A2 telemetry), the chain is tried cheapest-first. Responses carry `X-Blazar-Cascade: tried=… served=… reason=first-pass|escalated|none-passed` and usage summed across every attempted candidate; nobody-passed serves the last (strongest) candidate's answer. Streaming requests are rejected with a teaching 400 (a winner cannot be judged before completion), as are chains over 4 models and bodies over 1 MiB. Counters in `/metrics`: `blazar_cascade_runs_total`, `blazar_cascade_escalations_total`.

**`child_transport = "unix"`** — spawn children on Unix-domain sockets instead
of loopback TCP: each child listens on `run/<name>.sock` in the daemon's run
directory (next to its pidfile), and the gateway dials it over the same
socket, skipping the network stack and per-request port allocation. Socket
paths are deterministic per model, swept for stale files at daemon boot, and
unlinked when the child is evicted. Path budget is the OS `sun_path` limit
(~104B): a model name deep under a long `data_dir` fails fast with a
teaching error naming the offending component. Not available on Windows
(config validation rejects it there). `tcp` remains the default and is
byte-identical to previous releases.

### Federation: peers behind one gateway

`[[remotes]]` names other OpenAI-compatible servers (another blazar box, vLLM, an MLX server — anything speaking `/v1/*`). Requests for `<remote-name>:<model>` always route there explicitly. On top of that, with `remote_fallback = true` (default), a **bare** model name the local store does not know routes to whichever peer lists it: the gateway keeps a 60-second TTL cache of each peer's `/v1/models` listing, prefers the least-busy live peer, and never sends your caller credentials along — the peer's configured key rides instead, exactly as with explicit prefix routing. Locally-ambiguous names stay local (that is a naming problem), and a model no peer serves gets the ordinary local 404 teaching. Peer listings also merge into `GET /v1/models` (snapshot of the cache; the first fallback warms it). Set `remote_fallback = false` to roll the whole feature back to pure-prefix routing.

Fallback covers the OpenAI surfaces (`/v1/chat/completions`, `/v1/completions`, `/v1/embeddings`, `/v1/images/generations`), and the Ollama-compatible `/api/chat` (the request is translated to the peer and the reply back into ollama shape). `/api/generate` stays local-only: it refuses remote prefixes explicitly, so fallback honors the same contract. When a peer starts serving a model inside the TTL window, the first miss for that name triggers one throttled re-probe per peer (at most one every 10 seconds), so new peer models are found without per-request probe traffic.

### Structured output across dialects

One guarantee, three request dialects: the response never silently violates
the schema the caller asked for. Engines enforce schemas natively per request
(llama.cpp / mistral.rs convert the schema to a GBNF grammar); blazar adds the
cross-dialect plumbing and the post-hoc sentinel check.

| Dialect | Caller asks via | Translation | Guarantee |
|---|---|---|---|
| OpenAI | `response_format` (`json_object` / `json_schema`) | pass-through to child | child grammar + sentinel 422 on violation (non-streaming, `sentinel_enforce` / `X-Blazar-Enforce`) |
| Ollama | `format`: `"json"` or a JSON-schema object | `format` → `response_format` (translate.rs) | same as OpenAI once translated |
| Anthropic | forced tool: `tool_choice` `{"type":"tool","name":…}` + tool `input_schema` | → OpenAI forced-function `tool_choice` | child binds the named tool's schema; nameless forcing is rejected 400 at the boundary |
